# 多平台登录与广告接入

2026-10-23：游戏启动通过统一平台入口选择登录适配器；广告平台独立配置。当前实际登录仍只接微信，微信 PHP 请求格式及正式域名保持原样。本次无需重新部署 PHP，也没有变更数据库。

## 当前状态

| 发行渠道 | channel | 登录 | 广告 |
| --- | --- | --- | --- |
| 浏览器预览 | `web` | 保持本地预览流程 | 测试环境可使用模拟器 |
| 微信小游戏 | `wechat-mini` | 已接 `wx.login` 和 PHP `/auth/wechat` | 预留独立提供者，未接真实广告 SDK |
| 抖音小游戏 | `douyin-mini` | 预留，缺少适配器时阻止进入游戏 | 预留 |
| TapTap 小游戏 | `taptap-mini` | 独立预留 | 预留 |
| TapTap 安卓包 | `taptap-android` | 独立预留，需要原生 SDK 桥接 | 可另选原生广告 SDK |

TapTap 两种形态不共享一个假定的 SDK 实现。具体平台凭证、原生桥接和广告回调以之后实际选择的 SDK 为准。测试中的 TapTap 凭证和广告提供者均为内存替身，不代表已经完成平台联调。

## 代码分工

- `assets/scripts/platform/PlatformTypes.ts`：登录凭证、HTTP 传输、发行渠道和广告配置的接口。登录凭证允许包含多个字段，不限定所有平台必须返回微信式 `code`。
- `assets/scripts/platform/PlatformConfig.ts`：各渠道公开 AppID / Client ID、广告提供者名称及业务广告位到平台广告位 ID 的映射。微信 AppID 已从公共后端地址配置移到这里。
- `assets/scripts/platform/WechatPlatform.ts`：封装 `wx.login`、AppID 核对和 `wx.request`。仅发送 `{code}`，平台返回的额外身份字段不上传。保持 SDK 方法的宿主绑定。
- `assets/scripts/platform/PlatformServices.ts`：分别注册登录适配器和广告提供者，向启动流程提供统一入口。
- `assets/scripts/session/GameLogin.ts`：只负责凭证提交、游戏 UID / Bearer 会话、超时、401 重登、退出和销毁。响应中的 `provider` 和 `app_id` 必须匹配所选登录适配器。
- `assets/scripts/session/GameBackendConfig.ts`：各环境共享的 PHP API 地址。
- `assets/scripts/session/RewardedAds.ts`：所有玩法共用的广告请求、取消、重复回调隔离和清理。HUD 和奖励计算无需知道广告 SDK 名称。

发行渠道、后端身份命名空间和广告提供者是三个概念。例如 `taptap-android` 可以使用 TapTap 登录和另一个广告 SDK。业务中的 `weapon-daily`、`mine-reward` 等广告位保持稳定，由所选广告提供者读取渠道自己的 `ads.unitIds`。

## 平台选择

微信和抖音使用 Cocos 构建标记选择渠道，不根据全局对象是否碰巧有 `wx` 自动选择登录。其他包在启动场景前注入公开渠道配置：

```js
// TapTap 小游戏，需另行接入对应构建工具和 SDK。
globalThis.__FOREST_GUNNER_PLATFORM__ = { channel: 'taptap-mini' };
// TapTap 安卓包则在原生构建中使用 { channel: 'taptap-android' }。
```

微信/抖音构建与注入渠道冲突、原生构建缺少发行渠道、渠道名称无效时均报错，不会自动跳过登录进入本地玩法。浏览器无渠道配置时仍采用原来的本地预览。当前发布工具仍只构建 Web 和微信；预留渠道不等于已经提供抖音或 TapTap 成品包。

## 接入下一平台的步骤

1. 在 `PlatformConfig.ts` 填该渠道公开 AppID / Client ID。AppSecret 和服务端校验密钥仍只保存在 PHP 的环境配置。
2. 新建平台适配器，实现 `PlatformLoginBinding`：`provider.acquireCredential` 获取当前账号的凭证，`transport.request` 适配该端 HTTP API。原生 SDK 通过桥接返回凭证，不能在客户端伪造玩家 UID。获取凭证失败或用户取消应调用 `fail`；返回的取消函数用于超时、退出和销毁时终止等待。SDK 自身监听应在完成或取消时释放。
3. 在 `createDefaultPlatformProviders()` 注册 `.registerLogin(channel, factory)`。适配器给出与服务端约定的 `identityProvider`、`appId` 和相对登录路径。SDK 初始化也放在平台接入代码中，游戏启动和玩法不用增加渠道判断。
4. PHP 添加对应的请求参数校验、平台凭证验证器和明确路由，再复用玩家及会话服务。目前 PHP 的 `IdentityProvider.exchange(string $code)` 只实现微信；接多字段原生凭证时需要同步扩展服务端凭证契约，不能直接把它发往 `/auth/wechat`。客户端接口已支持多字段，其他平台服务端尚未实现。
5. 广告另外实现 `RewardedAdProvider`，通过 `.registerAds(providerName, factory)` 注册，并在对应渠道的 `ads.provider` / `ads.unitIds` 选择。该工厂可以读取渠道配置及宿主对象，不依赖登录 SDK。只在确认完整观看后回调 `success`，取消或失败不能发奖；返回请求清理函数，提供 `destroy` 释放 SDK。
6. 实机验收授权取消、切换账号、超时重试、前后台切换、广告重复回调、退出与销毁。现有广告服务会在切后台时取消请求；接真实 SDK 时必须验证该平台原生广告的生命周期行为。

广告总开关仍在 `ContentConfig.ts`，默认关闭；奖励数值仍在 `EconomyConfig.ts`。测试环境开启广告后仍用模拟面板，正式环境默认使用 `unavailable` 并返回失败。未知广告提供者会报配置错误，不会回退到模拟成功。

## 后端与存档边界

各端可以连接同一套自建 PHP API 和数据库。后端当前使用 `provider + app_id + openid` 区分平台身份，再关联游戏 UID；不同平台账号不会自动合并。跨平台共享同一玩家进度需要之后实现经过验证的账号绑定和服务器存档。

本次只改接入层，游戏存档、签到、兑换码及广告奖励仍沿用当前本地逻辑，未实现服务器权威结算或广告服务端回调验签。客户端广告 `success` 不能当作未来服务器发奖的可信凭据。
